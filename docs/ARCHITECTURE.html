Firmware Daemon — visio-recorder

As-built via the Epic 5 daemon-glue plan (issue #7, PR #15). Single Python systemd service, main() composes already-unit-tested parts. As built (PR #101): today's next_led_state resolves a confirmed battery halt to LedState.HALTED, red and solid, ahead of every other state, and the halt path applies it after the worker join so nothing can paint over it. Looks and priority belong to the LED state machine card below (the Halted, battery row).

Ws2812LedDriver writes one SPI transfer per colour to /dev/spidev0.0 through py-spidev (python3-spidev: no root, no /dev/mem, nothing compiled on the device). Each WS2812B bit is one byte at a 6.4 MHz request - 0xC0 for a 0, 0xF0 for a 1 - sent green, red, blue, MSB first, between two 240-byte zero resets (300 us latch). Both Zero 2W core clocks divide to a real 6.25 MHz, giving 320/960 ns and 640/640 ns pulses, at least 40 ns inside the WS2812B-V5 datasheet windows (legacy pre-V5 parts fall 10-40 ns outside theirs, a bench check). Pulsing and flashing render solid on the single pixel. LedController wraps the driver as the pixel's single owner (built, PR #100), and the Flag saved overlay is built too: a 150 ms magenta blink played on the controller's own thread, then restored to the resolved state. Looks and priority belong to the LED state machine card below. The device needs dtparam=spi=on, core_freq_fixed=1 (the kernel caches the core clock at probe, so a scaling core clock would skew the SPI rate) and the daemon user in the spi group.

Flag press path (local-first)

The device is the source of truth for a flag; the network is an opportunistic sync. A press is complete once the marker is durable, and the wearer is told so on the LED without waiting for WiFi.

flowchart TD

  C -- yes --> X["dropped\n(bounce, double-tap)"]
  C -- no --> WR["write the marker file,\nfsync it and the queue dir"]
  WR --> ACK["ack_flag(): magenta 150 ms\non the controller's thread,\nthen restore the state"]
  ACK --> SUB["submit it to the\nflag-upload worker\n(callback thread returns)"]
  SUB --> U{"upload\nthe marker"}
  U -- ok --> DEL["unlink it\nfrom the queue"]
  U -- fails --> RET["stays queued; retried\nin process, 30 s to 480 s,\nown failure counter,\na round stops at\nits first failure"]
  RET --> U
  SEG["upload worker, once the\n3 s restart gap has passed,\nbefore any segment and\nbefore each retry round"] -. "flush request" .-> U

Three properties are load-bearing. The acknowledgement blink is a momentary overlay rather than a state, so it has no rung in the LED precedence and returns the pixel to whatever the conditions last called for - including a latched CRITICAL red, which it is deliberately allowed to interrupt, since a long outage is exactly when a press most needs acknowledging. Marker retry lives in FlagUploadWorker and uses the shared RetryBackoff and next_worker_step, but its own consecutive-failure counter: a marker is metadata, so failing to send one must not by itself escalate the CRITICAL that means lost video. And every pending marker is uploaded before any segment - markers-first in the startup flush, and through that flush request while the daemon runs - and that flush waits until the segment's end plus the 3 s restart gap, so a press in the gap still goes up ahead of the segment it flags. The nightly run rarely sees a segment whose flags have not arrived; the pipeline's late-marker DLQ retry stays the backstop for when it does.

LED state machine designed 2026-11-19, partly built

The pendant runs concurrent regions - it can record and upload at the same moment - and one pure resolver projects them onto the single LED. The capture region (PR #103's recording control) always wins the look; health conditions only colour it while Recording; upload progress never shows on the LED (backup status is in the app, as with Limitless, Plaud, GoPro and Narrative Clip). Dark means no power or no daemon, never "recording quietly". This page and the pendant spec own the LED table for PRs #100, #101 and #103.

The upload queue is the queue/ directory on the SD card: finished segments and flag markers not yet uploaded. It survives reboots, every boot flushes it, and "draining" means letting the upload in flight finish, never the whole backlog. Gestures, one hold ladder in every state with LED previews: under 2 s flags (Recording) or rescans (Setup needed); 2-5 s starts recording, retries the camera, or stops (committed at 2 s while Recording); 5-10 s powers off safely from any state; 10 s or more re-onboards from Stopped. Running is a parent state, so its graceful power-off edge (hold, SIGTERM or a finished battery drain) and the ungraceful power-cut edge apply to every state inside it. Turning back on after a power-off is an open M2 hardware question (PiJuice button, or replug). Open M3 decision: upload whenever online (today), only while charging (GoPro, Narrative Clip), or while recording only above a charge threshold.

Key as-built decisions

  • rpicam-vid invoked once per segment (not one long-running --segment process) — filename/timing control at capture start, ~1-2s inter-segment gap accepted. Each run is passed -s (--signal), which costs nothing until a signal is sent and is what makes a capture interruptible.
  • The capture is the one command that runs through an interruptible runner: SubprocessInterruptibleRunner polls Popen.wait every 200 ms, and when the loop's stop event is set it sends SIGUSR2 (rpicam-vid's documented quit, which finalises the file), escalating to SIGTERM and then SIGKILL after 5 s each. The mux, the oversize split and the ALSA probe keep the plain blocking CommandRunner. A cut-short capture is not an error: it returns its path, is muxed, queued and uploaded like a full segment, and a non-zero exit after a cancel is reported rather than raised. Only a cancel landing before the first frame leaves nothing to mux - an empty file, or none at all - and that is discarded instead of queued. Measured end to end with a simulated camera: a stop that used to wait out the rest of the segment (6.2 s of an 8 s segment) now returns in 0.3 s and keeps the 2.1 s already recorded.
  • Segment size is pinned, not defaulted: --width 1280 --height 720 --framerate 30 --bitrate 4000000 are passed explicitly, and the default segment length (60 s) is derived from the bitrate so a segment fits the hosted 50 MiB upload limit with a 1.66x margin. See the segment size contract below.
  • Upload retry is in-process, owned by the existing upload worker: while segments are queued it blocks on its work queue only until a retry deadline, armed when the queue becomes non-empty and again after each round, and retries everything still queued once that deadline passes. A segment arriving does not restart the deadline, so a steady stream of segments cannot postpone a round. Each deadline is set from the backoff when armed, doubling per consecutive failure from 30 s to a 480 s cap and indexed by the same UploadHealth counter that drives the CRITICAL LED, so retry failures escalate and a retry success clears it. The decision is the pure next_worker_step, unit-tested without threads. A stopping worker never starts a round, and a round that tries no file (the queue emptied, or it was cancelled before its first file) leaves the counter and the LED untouched. No second thread and no scheduler; a new segment or the shutdown sentinel still wakes the worker at once, and a round in flight stops early once the loop is shutting down so a backlog is never uploaded through a battery halt. The startup flush is now the backstop rather than the only retry, for flag markers too: FlagUploadWorker runs the same decision over its own queue (see the flag press path above). Planned (LED state machine): the backoff gets its own attempt counter, advanced by rounds skipped for lack of NetworkManager connectivity full, so the 30-480 s schedule still settles offline while UploadHealth counts only failures on a working connection.
  • A flag press is durable before it is acknowledged and acknowledged before it is uploaded: write_flag_marker fsyncs the marker and the queue directory, the press handler then asks LedController for a 150 ms magenta blink, and only then hands the path to the flag-upload worker. The blink runs on the controller's own thread with its wait outside the controller's lock, so the gpiozero callback thread neither sleeps nor touches the driver, and a real state change landing mid-blink wins.
  • Flag markers travel with their footage. flush_pending drains markers before segments (markers_before_segments), and while the daemon runs the upload worker asks the flag-upload worker to flush its pending markers - before the segment it just recorded and before each retry round - and waits, the flush itself bounded at 30 s. Before that flush the worker waits until the segment's end plus the 3 s restart gap, since a press in that gap flags the segment that just ended and its marker would otherwise be uploaded after that segment; the gap wait is capped at the gap, so it never holds an upload longer than 3 s, and a retry round waits on the newest segment the run has queued. Once the loop is stopping (a stop, shutdown or battery halt) the gap is not waited and the flush is bounded at 5 s (STOP_MARKER_FLUSH_TIMEOUT_SEC): markers on the card still go up ahead of every segment the drain uploads, the cut-short last segment included, without a 30 s flush spending systemd's TimeoutStopSec=30; flags are only taken while recording, and a press in those last seconds goes up on the flag-upload worker's retries or the next boot's flush. A capture that wrote no footage is discarded before the worker sees it, so it costs no flush and does not move the end time a retry round waits on. Markers keep exactly one uploader, so the two threads never race one, and if the flush cannot finish the segment is still uploaded: footage outranks marker ordering, and the pipeline's late-marker handling is the backstop.
  • The pendant never writes devices: its device id comes from claim_pairing and is saved in device.json with a "pairing": 2 marker, so a pendant onboarded under the old contract rescans. Every pairing step is resumable after a power cut. The battery boot check runs before this gate, so a flat pendant powers off without scanning or signing in; the gate's one client backs the segment uploader, the status reporter and the flag-upload worker, which starts only after the gate, and every early exit closes the LedController. See Device Pairing.
  • device_status.recording_active is upserted true before the first capture and false after the worker drain on every exit path (stop, halt, capture failure); both pushes log and swallow errors.
  • The stop path's worker_thread.join() has no timeout; the halt path's is bounded by UPLOAD_DRAIN_TIMEOUT_SEC (120 s). On a halt the HALTED LED is applied after the join, so it is the final state and never raced by a slow in-flight upload. The bound exists because a dying battery is exactly when an upload is most likely to hang on a weak signal, and waiting forever for it ends in a brownout rather than a power-off. A stop pending or arriving during the halt drain caps the rest of it at STOP_HALT_DRAIN_TIMEOUT_SEC (15 s), so the power-off still lands inside TimeoutStopSec=30; a stop that cuts a capture short ends as a stop, and the next boot's battery check confirms the halt.
  • Shutdown is bounded by the unit, not by the segment length: KillMode=mixed so systemd signals only the daemon (the default control-group mode would signal rpicam-vid too and lose the segment the daemon is finalising), and TimeoutStopSec=30 in place of systemd's 90 s default, which the old segment-long stop used to run into.
  • The upload-failure CRITICAL LED is latched, not momentary: both of on_segment_complete's LED states are derived from the shared UploadHealth counter, and upload_critical outranks low battery and uploading in next_led_state. Red therefore survives the following segments' upload blue and recording green until the success that resets the counter. Previously the worker applied red only after those two colours had already been written, so a sustained outage looked normal for most of every segment.
  • A battery halt is a shutdown sequence, not an exit: no decision is taken on one gauge sample (a moving average plus consecutive confirmations), a voltage floor sits beside the percentage because the gauge lags under camera and WiFi load, nothing halts while externally powered, and a confirmed halt drains the queue under a bound, shows Halted solid red, then arms wake-on-charge and powers off cleanly. The old behaviour flashed red and exited 0, leaving an idle Pi to discharge to zero and brown out mid-write - the single most likely way this device corrupts an SD card. Recovery needs no human either way: charge arriving during the drain cancels the halt and re-enters the loop with the upload-failure latch and the day's upload count intact, a failed re-read never blocks the power-off, a gauge that stays unreadable for three readings halts rather than recording blind, and charge arriving after it is caught by the HAT's wake. See the battery and power management card above.

Battery and power management

A fuel gauge reports state of charge, not energy, and the pendant's own load - a 4 Mbps hardware H.264 encode plus a WiFi upload burst - makes both the reported percentage and the cell's terminal voltage dip and recover. So no decision is taken on one sample, and a confirmed halt ends in a clean power-off rather than an exit that leaves an idle Pi discharging until it browns out mid-write.

ThresholdValueEffect
BATTERY_WARN_PCT20sets the low-battery latch (yellow LED)
BATTERY_WARN_CLEAR_PCT25clears it - a 20-25 % hysteresis band, so a battery hovering at the line does not flicker the LED all afternoon
BATTERY_HALT_PCT10halts after HALT_CONFIRMATIONS (3) consecutive smoothed samples below it; the same count of consecutive failed readings halts too, with reason unreadable, while a single failed reading keeps the last verdict; at boot the first reading is retried that many times and an unreadable gauge refuses the boot and powers off
BATTERY_FLOOR_MV3300halts after FLOOR_CONFIRMATIONS (2) consecutive raw samples below it - the floor exists because the percentage lags under load, so smoothing it would reintroduce the lag it covers
PCT_AVERAGE_WINDOW5samples in the percentage moving average; a shorter run averages what has arrived rather than running unguarded
WAKE_ON_CHARGE_PCT25SetWakeUpOnCharge level, armed before the power-off so the HAT re-powers the Pi on its own
UPLOAD_DRAIN_TIMEOUT_SEC120how long a halt waits for the queue to drain before powering off

10 % and 3300 mV are PiJuice's own shipped defaults for the same two jobs (min_charge.threshold and min_bat_voltage.threshold), which keeps the firmware's software halt and the HAT's independent system-task backstop from disagreeing about when the battery is empty. No halt is ever returned while externally powered (powerInput or powerInput5vIo reading PRESENT, or the battery reading NOT_PRESENT): both confirmation counts reset, which is what PiJuice's own pijuice_sys.py does too. The decision lives in one pure object, BatteryMonitor, which reads no hardware and keeps no clock, so noisy, sagging, charging and recovering traces are ordinary test inputs.

The battery is sampled on the main loop thread at the cadence it already was - once per segment - and no monitor thread is added, because a second thread would need a share of the LED and the single-owner invariant is worth more than a faster poll. The honest consequence is that the software voltage floor reacts in FLOOR_CONFIRMATIONS x the segment length, about two minutes. The margin that covers is the PiJuice's own system task (min_charge, min_bat_voltage, wakeup_on_charge), which halts the Pi whether or not the daemon is healthy; arming it needs the HAT, so it is a bench step rather than firmware. systemctl poweroff is privileged and the daemon is not root, so a polkit rule for org.freedesktop.login1.power-off ships beside the systemd unit. A confirmed halt always powers off; there is no switch to suppress it.

BatteryReader stays a one-method protocol (get_charge_pct); voltage and external-power state are a second, richer BatteryTelemetryReader, and a percentage-only source is read for percentage alone with no voltage to compare against a floor. That is what keeps VISIO_BATTERY_SOURCE=none (the USB power bank, a fixed 100 %) provably unchanged by all of the above.

Segment size contract

The hosted project rejects any object over 50 MiB (free plan, cannot be raised). Before this contract the firmware left size to rpicam-apps defaults (640x480 at the V4L2 encoder's 10 Mbps): a 5-minute segment was ~375 MB, rejected in production and retried on every boot forever. Locally it uploaded fine, because config.toml's file_size_limit is not what the CLI's storage container enforces.

Recording Stop/Start Control

From the recording stop/start design spec (accepted 2026-11-18). The pendant gets a hold-to-toggle record button, a stopped state the wearer can see on the LED and in the app, and a boot that comes up stopped. It ships in phases; only phase 1 has landed, so everything below marked designed is the plan, not today's behaviour.

Stopping a recording

flowchart TD
  T["SIGTERM / SIGINT\n(systemctl stop, poweroff)"] --> H["handler sets stop,\nwhich is the capture's cancel event"]
  H --> C["the interruptible capture runner\nnotices within 200 ms"]
  C --> U["SIGUSR2 to rpicam-vid:\nfinalise the file and quit"]
  U -- "still running after 5 s" --> TERM["SIGTERM"]
  TERM -- "still running after 5 s" --> KILL["SIGKILL"]
  U --> S["a complete, shorter segment"]
  TERM --> S
  KILL --> S
  S --> M["mux and queue\nthe cut segment"]
  M --> D["recording_active=false,\nwell inside TimeoutStopSec=30"]
  D --> W["the worker drains the queue;\nan upload cut off by the budget\nresumes on the next boot"]

Before this, the loop observed the stop only between segments, so a stop waited up to a whole segment - 300 s measured on the device with the old five-minute segments, 60 s with today's derived default - and systemd's 90 s default stop timeout turned the overrun into a SIGKILL that lost the in-flight segment.

A RecordingControl object will own three events - recording, cancel_capture and wake - so the gpiozero callback thread and the signal handler only set events and every transition is observed on the main thread. Phase 1 uses the loop's existing stop event as the cancel event, which is the same mechanism with one caller.

Decisions, ruled on 2026-11-18

  • Remote control from the app: display only. The app shows Recording or Stopped live and has no control, so no device_commands table, no inbound firmware channel and no new attack surface on a wearable camera.
  • Daemon crash-restart inside one power cycle: resume the wearer's last choice via a /run marker that any reboot clears, so a crash continues the session the button started while a reboot still comes up stopped.
  • Completing first-boot onboarding: the device stays stopped and waits for a hold - the first thing a new wearer learns is that the button is what starts it.
  • Short press while stopped: ignored. A hold toggles in both directions, so the gesture is symmetric and blind-operable, and a tap in a bag never starts a camera.

Aligned with the pendant spec's LED state machine (PR #102): precedence is HALTED > SHUTTING_DOWN > STOPPED (when not recording) > CRITICAL > LOW_BATTERY > RECORDING, so no health colour ever shows over STOPPED, and uploads, which run concurrently, never show on the LED. A hold from RECORDING stops at 2 s; a hold from STOPPED commits on release (2-5 s starts recording, 10 s or more re-onboards); a 5 s hold in any state powers off gracefully through SHUTTING_DOWN; green, white-pulsing and cyan previews read from gpiozero's held_time.

Open bench checks (none block a PR). BENCH-1: that rpicam-vid -s exits 0 on SIGUSR2 and the cut .h264 and .ts remux with ffmpeg -c copy - the runner tolerates a non-zero exit, so a failure degrades to the orphan-recovery path rather than a lost segment. BENCH-2: that a 2 s hold is reliably distinguishable from a tap through clothing. BENCH-3: that cancel, mux, enqueue and the final recording_active=false push on a Zero 2W fit inside TimeoutStopSec=30; they run before the upload drain, so an upload the budget cuts off leaves the app correct and its segment queued for the next boot.

As-built gaps

Known, tracked deviations from the spec — not hidden, not yet fixed. Both previously tracked firmware gaps are closed; one hardware substitution and the LED SPI rewire's follow-ups are open:

Manual flag button wired (issue #18). main() registers a gpiozero listener on GPIO 17 (pull-up, 50ms bounce) whose handler debounces, writes the FLAG_YYYYMMDD_HHMMSS.marker, fsyncs the file and the queue directory, asks the LedController for a 150 ms magenta acknowledgement blink, and hands the path to a dedicated flag-upload worker thread that uploads it immediately (the gpiozero callback thread touches neither the network nor the driver); a 2s cooldown drops bounce/double-taps. A failed upload is retried in process on the segments' backoff by that same worker, which stays the only uploader of a marker, and the next boot's markers-first flush is the backstop.
NetworkManager keyfile activated after write (issue #19). After onboarding, main() runs nmcli connection reload then nmcli connection up visio behind a ConnectionActivator protocol. On failure: CRITICAL LED, exit 1; keyfile + pairing code are on disk, so systemd restart + NM autoconnect retry from there. Restart boots also retry the reload/up best-effort whenever the keyfile exists (NM does not reliably load dropped-in keyfiles on its own); that retry never fails the boot.
LED SPI rewire: provisioning follow-ups and bench checks open (2026-11). The firmware now drives the LED over SPI0 MOSI, freeing GPIO 18 for I2S audio and removing the /dev/mem need that kept the daemon on root. Draft PR #26 still installs and checks rpi_ws281x; it needs python3-spidev, SPI and core_freq_fixed=1 enabled, and a spidev preflight check. Dropping root additionally needs onboarding to create the WiFi profile with nmcli connection add instead of writing a keyfile (NetworkManager rejects non-root-owned keyfiles, and its D-Bus policy denies ReloadConnections to non-root callers), a visio user in video gpio i2c spi and a polkit rule for settings.modify.system + network-control. On the bench: move the data wire to header pin 19, check each colour, confirm a 3.3 V data line drives the WS2812B reliably, and confirm the fitted part is a WS2812B-V5. Full list: provisioning spec, LED SPI rewire follow-ups.
PiJuice deferred to a USB power bank (2026-07-21). The spec's PiJuice Zero pHAT is currently blocked on availability; bring-up and integration testing run on a generic USB power bank into the Pi's power input instead — no HAT, no I2C battery telemetry. Firmware handles this via a new VISIO_BATTERY_SOURCE config (pijuice default, or none → a new UnmeteredPowerReader that reports a fixed 100% so the halt/low-battery thresholds never false-trigger while mains-equivalent powered), and the preflight check treats missing PiJuice hardware as a warning, not a startup-blocking failure. See the provisioning & preflight spec. BatteryReader is a Protocol, so a real replacement (PiSugar 2/3, a generic I2C-fuel-gauge UPS HAT, or a hand-built TP4056/IP5306 + MAX17048 combo) is a contained future swap, not a firmware rewrite. It stays a one-method protocol for exactly that reason: the battery-hardening work put voltage and external-power telemetry in a second protocol rather than widening this one, so a source that can only report a percentage - this power bank included - needs no change and reaches none of the new halt paths.

Segment duration contract

A segment's length is a property of its file, never of the recording config: the firmware's nominal length (one minute by default) is only an upper bound (stop press, crash, dead battery). Prerequisite for start/stop recording.

  • Firmware names the segment after its capture start and muxes it with the capture framerate, so the MP4's container duration is real. It reports duration nowhere else.
  • Pipeline downloads and ffprobes every segment before matching flag markers. No measurable duration → pipeline_dlq rejected; a failed download fails the device day for retry.
ConsumerRule
Flag-marker window[recorded_at, recorded_at + duration); a marker up to 3 s after a segment ends (the restart gap between captures) flags that segment; one further into a gap is unmatched
Clip extractionmin(15 s, duration), centred at (duration - clip) / 2, always inside the file
Vision frames3 frames spread over the real duration (fps=3/<duration>)
segments.duration_secwhole seconds, rounded up (one-second markers stay covered); rewritten on re-run
reels.duration_secprobed from the assembled reel, nearest second; >1 s off the clip total is logged as a dropped clip
Silent segments scored, not failed. A pendant without a working microphone records video only and ffmpeg refuses to extract audio from a file with no audio stream, which failed every real device day in Stage 1. A segment with no audio stream now scores as silence without a Whisper call.

Retention and cleanup designed 2026-11-19, not built

Data model

devices.device_user_id (unique, the pendant's anonymous auth user) and private.device_pairing_codes (SHA-256 of a 256-bit code, single use). Helpers private.owned_device_ids() and private.paired_device_id() are the one place every policy asks who may act for a device.

Permissions

The owner reads; the device user writes only its device's device_status row and uploads only into segments/{device_id}/, reading back only its own uploads. The owner loses direct inserts on devices and all storage writes. The pipeline (service role) is unchanged.

Lifecycle

Policies resolve the link at query time, so Remove device revokes at once even while the pendant's access token is still valid. Re-pairing deletes the previous device user. App logout touches only the phone's session. The login never expires by time. A boot restores it with the refresh-token grant and unpairs only on GoTrue's codes for a gone token, session or user, so a pendant booting before NTP sync is never unpaired. During the run the firmware refreshes the login itself, on demand before each upload and status write, so a pendant that was offline when its hourly refresh fell due recovers once back on Wi-Fi. A daily pg_cron job deletes anonymous users no device points at.

Manual step: anonymous sign-ins must be enabled on the hosted project (CAPTCHA off, no session time-box), the migration applied, firmware and app shipped together, and the test pendant re-onboarded once. Firmware rejects the old v1 QR payload rather than accept the owner's session again. The old pendant's copy of the owner's phone session is deleted from its disk but stays valid on the server until the phone signs out, so sign out and back in on the phone after re-onboarding.
