Firmware Daemon — visio-recorder

As-built via the Epic 5 daemon-glue plan (issue #7, PR #15). Single Python systemd service, main() composes already-unit-tested parts. Runs on Raspberry Pi OS Lite trixie (Debian 13, 64-bit headless), verified on the device during provisioning bring-up; the spec originally targeted Bookworm. The firmware's Python floor stays 3.11 while trixie ships 3.13.

18, 19, 20 (12, 35, 38)I2S microphone (INMP441)PCM_CLK, PCM_FS, PCM_DIN; GPIO 21 (PCM_DOUT) is claimed by the same pin group. Never enable SPI1 (CE0/CE1 = GPIO 18/17).

Ws2812LedDriver writes one SPI transfer per colour to /dev/spidev0.0 through py-spidev (python3-spidev: no root, no /dev/mem, nothing compiled on the device). Each WS2812B bit is one byte at a 6.4 MHz request - 0xC0 for a 0, 0xF0 for a 1 - sent green, red, blue, MSB first, between two 240-byte zero resets (300 us latch). Both Zero 2W core clocks divide to a real 6.25 MHz, giving 320/960 ns and 640/640 ns pulses, at least 40 ns inside the WS2812B-V5 datasheet windows (legacy pre-V5 parts fall 10-40 ns outside theirs, a bench check). Pulsing and flashing render solid on the single pixel. The device needs dtparam=spi=on, core_freq_fixed=1 (the kernel caches the core clock at probe, so a scaling core clock would skew the SPI rate) and the daemon user in the spi group.

Key as-built decisions

  • rpicam-vid invoked once per segment (not one long-running --segment process) — filename/timing control at capture start, ~1-2s inter-segment gap accepted. Each run is passed -s (--signal), which costs nothing until a signal is sent and is what makes a capture interruptible.
  • The capture is the one command that runs through an interruptible runner: SubprocessInterruptibleRunner polls Popen.wait every 200 ms, and when the loop's stop event is set it sends SIGUSR2 (rpicam-vid's documented quit, which finalises the file), escalating to SIGTERM and then SIGKILL after 5 s each. The mux, the oversize split and the ALSA probe keep the plain blocking CommandRunner. A cut-short capture is not an error: it returns its path, is muxed, queued and uploaded like a full segment, and a non-zero exit after a cancel is reported rather than raised. Only a cancel landing before the first frame leaves nothing to mux - an empty file, or none at all - and that is discarded instead of queued. Measured end to end with a simulated camera: a stop that used to wait out the rest of the segment (6.2 s of an 8 s segment) now returns in 0.3 s and keeps the 2.1 s already recorded.
  • Segment size is pinned, not defaulted: --width 1280 --height 720 --framerate 30 --bitrate 4000000 are passed explicitly, and the default segment length (60 s) is derived from the bitrate so a segment fits the hosted 50 MiB upload limit with a 1.66x margin. See the segment size contract below.
  • Upload retry is in-process, owned by the existing upload worker: while segments are queued it blocks on its work queue only until a retry deadline, armed when the queue becomes non-empty and again after each round, and retries everything still queued once that deadline passes. A segment arriving does not restart the deadline, so a steady stream of segments cannot postpone a round. Each deadline is set from the backoff when armed, doubling per consecutive failure from 30 s to a 480 s cap and indexed by the same UploadHealth counter that drives the CRITICAL LED, so retry failures escalate and a retry success clears it. The decision is the pure next_worker_step, unit-tested without threads. A stopping worker never starts a round, and a round that tries no file (the queue emptied, or it was cancelled before its first file) leaves the counter and the LED untouched. No second thread and no scheduler; a new segment or the shutdown sentinel still wakes the worker at once, and a round in flight stops early once the loop is shutting down so a backlog is never uploaded through a battery halt. The startup flush is now the backstop rather than the only retry - and remains the only retry for flag markers, which FlagUploadWorker owns while the daemon runs.
  • Device registration retries independently of device-ID persistence (a separate device_registered marker, not device.json existence) — closes a retry gap found by no-mistakes' review step.
  • device_status.recording_active is upserted true before the first capture and false after the worker drain on every exit path (stop, halt, capture failure); both pushes log and swallow errors.
  • Shutdown is bounded by the unit, not by the segment length: KillMode=mixed so systemd signals only the daemon (the default control-group mode would signal rpicam-vid too and lose the segment the daemon is finalising), and TimeoutStopSec=30 in place of systemd's 90 s default, which the old segment-long stop used to run into.
  • Halt-path worker_thread.join() has no timeout — the CRITICAL LED is guaranteed to be the final state, never raced by a slow in-flight upload.
  • The upload-failure CRITICAL LED is latched, not momentary: both of on_segment_complete's LED states are derived from the shared UploadHealth counter, and upload_critical outranks low battery and uploading in next_led_state. Red therefore survives the following segments' upload blue and recording green until the success that resets the counter. Previously the worker applied red only after those two colours had already been written, so a sustained outage looked normal for most of every segment.

Segment size contract

The hosted project rejects any object over 50 MiB (free plan, cannot be raised). Before this contract the firmware left size to rpicam-apps defaults (640x480 at the V4L2 encoder's 10 Mbps): a 5-minute segment was ~375 MB, rejected in production and retried on every boot forever. Locally it uploaded fine, because config.toml's file_size_limit is not what the CLI's storage container enforces.

SideGuarantee
Storagesegments and reels buckets carry a 50 MiB file_size_limit, enforced on every stack
CaptureVISIO_VIDEO_WIDTH/HEIGHT/FRAMERATE/BITRATE (1280x720@30, 4 Mbps) passed to rpicam-vid explicitly
Segment lengthlongest 10 s multiple whose predicted size (video + 128 kbps audio reserve) / 8 x s x 1.02 uses at most 2/3 of VISIO_MAX_UPLOAD_BYTES: 60 s, ~31.6 MB, at the defaults
Oversize guarda file over the limit is split with ffmpeg -c copy -f segment into parts named by their start; a part storage still 413s is split again; an unsplittable one moves to rejected/, counts in device_status.segments_rejected, and is never retried; a split that fails for a passing reason (full SD card, ffmpeg failing with under twice the file size free) stays queued for the next in-process retry round or the next boot

Audio capture

An INMP441 I2S MEMS microphone (handoff option A, decided 2026-11-16). With a microphone, each segment is one rpicam-vid --codec libav --libav-format mpegts --libav-audio --audio-source alsa --audio-device visio_mic run: hardware H.264 plus 64 kbps mono AAC on one clock, written as MPEG-TS so a killed capture is still recoverable, then remuxed to MP4. Without one the pendant records video only.

Recording Stop/Start Control

From the recording stop/start design spec (accepted 2026-11-18). The pendant gets a hold-to-toggle record button, a stopped state the wearer can see on the LED and in the app, and a boot that comes up stopped. It ships in phases; only phase 1 has landed, so everything below marked designed is the plan, not today's behaviour.

Stopping a recording

flowchart TD
  T["SIGTERM / SIGINT\n(systemctl stop, poweroff)"] --> H["handler sets stop,\nwhich is the capture's cancel event"]
  H --> C["the interruptible capture runner\nnotices within 200 ms"]
  C --> U["SIGUSR2 to rpicam-vid:\nfinalise the file and quit"]
  U -- "still running after 5 s" --> TERM["SIGTERM"]
  TERM -- "still running after 5 s" --> KILL["SIGKILL"]
  U --> S["a complete, shorter segment"]
  TERM --> S
  KILL --> S
  S --> M["mux and queue\nthe cut segment"]
  M --> D["recording_active=false,\nwell inside TimeoutStopSec=30"]
  D --> W["the worker drains the queue;\nan upload cut off by the budget\nresumes on the next boot"]

Before this, the loop observed the stop only between segments, so a stop waited up to a whole segment - 300 s measured on the device with the old five-minute segments, 60 s with today's derived default - and systemd's 90 s default stop timeout turned the overrun into a SIGKILL that lost the in-flight segment.

A RecordingControl object will own three events - recording, cancel_capture and wake - so the gpiozero callback thread and the signal handler only set events and every transition is observed on the main thread. Phase 1 uses the loop's existing stop event as the cancel event, which is the same mechanism with one caller.

Decisions, ruled on 2026-11-18

  • Remote control from the app: display only. The app shows Recording or Stopped live and has no control, so no device_commands table, no inbound firmware channel and no new attack surface on a wearable camera.
  • Daemon crash-restart inside one power cycle: resume the wearer's last choice via a /run marker that any reboot clears, so a crash continues the session the button started while a reboot still comes up stopped.
  • Completing first-boot onboarding: the device stays stopped and waits for a hold - the first thing a new wearer learns is that the button is what starts it.
  • Short press while stopped: ignored. A hold toggles in both directions, so the gesture is symmetric and blind-operable, and a tap in a bag never starts a camera.

Aligned with the pendant spec's LED state machine (PR #102): precedence is HALTED > SHUTTING_DOWN > STOPPED (when not recording) > CRITICAL > LOW_BATTERY > RECORDING, so no health colour ever shows over STOPPED, and uploads, which run concurrently, never show on the LED. A hold from RECORDING stops at 2 s; a hold from STOPPED commits on release (2-5 s starts recording, 10 s or more re-onboards); a 5 s hold in any state powers off gracefully through SHUTTING_DOWN; green, white-pulsing and cyan previews read from gpiozero's held_time.

Open bench checks (none block a PR). BENCH-1: that rpicam-vid -s exits 0 on SIGUSR2 and the cut .h264 and .ts remux with ffmpeg -c copy - the runner tolerates a non-zero exit, so a failure degrades to the orphan-recovery path rather than a lost segment. BENCH-2: that a 2 s hold is reliably distinguishable from a tap through clothing. BENCH-3: that cancel, mux, enqueue and the final recording_active=false push on a Zero 2W fit inside TimeoutStopSec=30; they run before the upload drain, so an upload the budget cuts off leaves the app correct and its segment queued for the next boot.

As-built gaps

Known, tracked deviations from the spec — not hidden, not yet fixed. Both previously tracked firmware gaps are closed; one hardware substitution and the LED SPI rewire's follow-ups are open:

Manual flag button wired (issue #18). main() registers a gpiozero listener on GPIO 17 (pull-up, 50ms bounce) whose handler debounces, writes the FLAG_YYYYMMDD_HHMMSS.marker, and hands it to a dedicated flag-upload worker thread that uploads it immediately (the gpiozero callback thread never touches the network); a 2s cooldown drops bounce/double-taps, and a failed upload leaves the marker queued for next-boot flush; unlike segments it gets no in-process retry, so it never races the upload worker.
NetworkManager keyfile activated after write (issue #19). After onboarding, main() runs nmcli connection reload then nmcli connection up visio behind a ConnectionActivator protocol. On failure: CRITICAL LED, exit 1; keyfile + session are on disk, so systemd restart + NM autoconnect retry from there. Restart boots also retry the reload/up best-effort whenever the keyfile exists (NM does not reliably load dropped-in keyfiles on its own); that retry never fails the boot.
LED SPI rewire: provisioning follow-ups and bench checks open (2026-11). The firmware now drives the LED over SPI0 MOSI, freeing GPIO 18 for I2S audio and removing the /dev/mem need that kept the daemon on root. Draft PR #26 still installs and checks rpi_ws281x; it needs python3-spidev, SPI and core_freq_fixed=1 enabled, and a spidev preflight check. Dropping root additionally needs onboarding to create the WiFi profile with nmcli connection add instead of writing a keyfile (NetworkManager rejects non-root-owned keyfiles, and its D-Bus policy denies ReloadConnections to non-root callers), a visio user in video gpio i2c spi and a polkit rule for settings.modify.system + network-control. On the bench: move the data wire to header pin 19, check each colour, confirm a 3.3 V data line drives the WS2812B reliably, and confirm the fitted part is a WS2812B-V5. Full list: provisioning spec, LED SPI rewire follow-ups.
PiJuice deferred to a USB power bank (2026-07-21). The spec's PiJuice Zero pHAT is currently blocked on availability; bring-up and integration testing run on a generic USB power bank into the Pi's power input instead — no HAT, no I2C battery telemetry. Firmware handles this via a new VISIO_BATTERY_SOURCE config (pijuice default, or none → a new UnmeteredPowerReader that reports a fixed 100% so the halt/low-battery thresholds never false-trigger while mains-equivalent powered), and the preflight check treats missing PiJuice hardware as a warning, not a startup-blocking failure. See the provisioning & preflight spec. BatteryReader is a Protocol, so a real replacement (PiSugar 2/3, a generic I2C-fuel-gauge UPS HAT, or a hand-built TP4056/IP5306 + MAX17048 combo) is a contained future swap, not a firmware rewrite.

Composite score

base_score = 0.4 * scene_novelty + 0.3 * audio_activity + 0.2 * motion_intensity
score = base_score * 1.5  (if manually flagged)
      | base_score         (otherwise)

Weights are per-user, stored in score_weights, tunable via the mobile app.

Trigger (as-built): the pipeline runs as the nightly-reel GitHub Actions workflow - nightly cron at 19:00 UTC (02:00 device-local ICT), plus workflow_dispatch with an optional day input for manual runs. Supabase Edge Functions were ruled out (pipeline is Python + FFmpeg; Edge Functions run Deno), and the spec's pending-segment-count threshold trigger is not implemented. Keys a run cannot process land in pipeline_dlq for nightly retry; after 5 attempts the key is escalated and the device owner is notified via push.

Segment duration contract

A segment's length is a property of its file, never of the recording config: the firmware's nominal length (one minute by default) is only an upper bound (stop press, crash, dead battery). Prerequisite for start/stop recording.

  • Firmware names the segment after its capture start and muxes it with the capture framerate, so the MP4's container duration is real. It reports duration nowhere else.
  • Pipeline downloads and ffprobes every segment before matching flag markers. No measurable duration → pipeline_dlq rejected; a failed download fails the device day for retry.
ConsumerRule
Flag-marker window[recorded_at, recorded_at + duration); a marker up to 3 s after a segment ends (the restart gap between captures) flags that segment; one further into a gap is unmatched
Clip extractionmin(15 s, duration), centred at (duration - clip) / 2, always inside the file
Vision frames3 frames spread over the real duration (fps=3/<duration>)
segments.duration_secwhole seconds, rounded up (one-second markers stay covered); rewritten on re-run
reels.duration_secprobed from the assembled reel, nearest second; >1 s off the clip total is logged as a dropped clip
Silent segments scored, not failed. A pendant without a working microphone records video only and ffmpeg refuses to extract audio from a file with no audio stream, which failed every real device day in Stage 1. A segment with no audio stream now scores as silence without a Whisper call.
